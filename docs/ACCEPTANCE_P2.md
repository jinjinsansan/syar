## ★A-1 のメモリ計測についての訂正（2026-08-10）

1回目の A-1 報告で「メモリ **95 → 100 → 62 → 69 → 67MB** に増加傾向なし」と書きました。
**この数字はワーカーのものではありませんでした。**

`systemctl show -p MainPID` が **tsx のラッパー**を指しており、
**実際のワーカーは子プロセス**でした。ラッパーはほとんど何もしないので、
**あの推移はワーカーの状態を一切表していません。**

★**D-043 でラッパーが消え、この問題は構造ごと解消しました。**

```
配備後: MainPID = /usr/bin/node dist/worker.cjs （1本だけ）
        ps の 132,616 kB = 129MB  ＝ 自己報告 mem=129MB   ★一致
        fd 35 → 23 / sock 9 → 3 / handles 3 → 2
```

リークが無いという結論の根拠は、**プロセス内部から測った推移**です。

```
02:02 → 06:43   mem 158〜159MB / heap 27〜39MB / fd 35 / sock 9   ★不動
```

## ★A-1 のサイクル時間の再測（2026-08-11・R-23 による失効と更新）

### なぜ再測が要ったか

レビュー側の指摘:

> レース生成は「欠落なく前進」で通りましたが、**あれは116秒の観測**でした。
> 18頭立てが常態化すれば周が収まりません。

**A-1 の PASS は「1周116秒の世界」に対するものでした。** P3 でレースを実際に多数生成したところ、
**1本あたり 236〜976秒**かかることが分かりました（頭数で4倍以上のばらつき）。
1周は600秒で、生成は**2レース先まで**行うので、これは A-1 を脅かします。

### 原因は計算ではなく**投入**でした

CPU は27分のうち6.4分（**24%**）しか使っておらず、残りは I/O 待ちでした。
オッズを**1行ずつ 5,483回**投入していたためです（`pg-store.ts`）。

| | 1行ずつ | `unnest` で一括 |
|---|---|---|
| 17頭立て・4,652点 | **675.8秒** | **1.3秒** |

★**505倍**。そして**行は1つも変わっていません**（`tools/diag-insert.mjs` が全件突合）:
オッズの行数一致 / オッズの中身の差 **0行** / 出走表の差 **0行**。

### 再測した余裕（純計算・本番と同じ 3,896,104 試行）

| cycle | 頭数 | オッズ点数 | 計算時間 |
|---|---|---|---|
| 601 | 12 | 1,774 | 91秒 |
| 602 | 11 | 1,150 | **102秒** |
| 603 | 10 | 1,025 | 80秒 |
| 604 | 9 | 680 | 64秒 |
| 605 | **18** | 4,781 | **102秒** |

★**計算時間は頭数にほとんど依らず 64〜102秒**です。
**「頭数で4倍」は計算ではなく投入の話**でした（オッズ点数が 680 → 4,781 と7倍になるため）。

```
最悪 102秒 × 2レース先行生成 = 204秒
1周 600秒 に対する余裕 = 396秒（66%）
```
